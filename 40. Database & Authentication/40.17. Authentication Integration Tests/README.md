# Authentication Integration Tests

The completed application is the exact source demonstrated in the video.

- Starter/shopfront-next: the ShopFront app as completed in the previous lecture.
- Completed/shopfront-next: the app at the end of this lecture. Keep it for the next lecture.
- Not included: the private .env and Prisma's generated client folder (generated/), which you create as Run describes.

Direct HTTP tests through the real authentication handler: tests/auth.integration.mjs first checks its isolated origin and database, signs in Alex and Bob separately (a cookie for each; the supplied helper honours Retry-After) and asserts: no cookie gets 401; Alex reads O-1001; Bob's read and PATCH of it get 404; Alex's PATCH saves the note (read back); a foreign origin gets 403; Alex reads W-1 but not W-2; a Travel note addressed through the Studio workspace is rejected; a viewer can read but not write (the role is restored); the private page without a cookie redirects (307) to the account page; an invented cookie gets 401 from the API and the sign-in feedback from the page; a signed-out cookie and an expired session (moved into the past in shopfront_test) get 401. The launcher now runs this file, as `npm run test:auth`.

## Run

Work in C:\react\shopfront-next: continue your own working copy there, or copy this ZIP's Starter (to follow the video) or Completed shopfront-next folder there. No folder anywhere in the path may contain the & character, so never run npm inside the extracted section folder. Open the folder in VS Code. The ZIP leaves out the private .env file and Prisma's generated client (generated/): you create both below.

PostgreSQL must be running with the course role shopfront and its two databases, shopfront_dev (development) and shopfront_test (automated tests only), as set up in Setting the Environment: in SQL Shell, as the postgres administrator, `CREATE ROLE shopfront LOGIN;`, `\password shopfront` (a private password), `CREATE DATABASE shopfront_dev OWNER shopfront;` and `CREATE DATABASE shopfront_test OWNER shopfront;`. Reuse existing course databases; never drop or reset one.

Copy .env.example to .env (Git ignores it) and enter your own private values: in DATABASE_URL and DIRECT_URL (both shopfront_dev) and TEST_DATABASE_URL (shopfront_test) replace REPLACE_ME with the shopfront role's password, and 5432 with your PostgreSQL port if you chose another one. URL-encode special characters in that password (for example @ as %40, : as %3A, / as %2F, # as %23, % as %25), or they are read as parts of the connection string. Keep COURSE_ALLOW_WRITES=disabled in .env, in an .env.local left from the previous section, and in the terminal before you start Next (PowerShell: `$env:COURSE_ALLOW_WRITES="disabled"`; macOS/Linux: `export COURSE_ALLOW_WRITES=disabled`): a terminal value or .env.local takes priority over .env. Set BETTER_AUTH_URL=http://localhost:3000 and replace the BETTER_AUTH_SECRET placeholder with your own random secret, generated privately with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"` (never share it or commit it). GITHUB_CLIENT_ID and GITHUB_CLIENT_SECRET stay optional (OAuth Sign-In; callback http://localhost:3000/api/auth/callback/github): leave them empty to hide the GitHub button. Keep the local mail values from .env.example (SMTP_HOST=127.0.0.1, SMTP_PORT=2525, SMTP_SECURE=false, empty SMTP_USER and SMTP_PASSWORD, an example.test MAIL_FROM).

Stop any other app using ports 3000, 5211, 2525, 3041 or 3140 first. In a first terminal run `npm ci` (the first installation needs registry access), then `npm run db:check`: it prints the connected database (shopfront_dev) and user (shopfront), never the password. Then run `npm run db:deploy` (applies the saved migrations to shopfront_dev; a repeated run reports none pending), `npm run db:generate` (writes Prisma's typed client into generated/; rerun it, and restart Next, after every schema change) and `npm run db:seed` (the sample customers, products and order; safe to repeat, and it restores the sample stock), then `npm run db:fixtures` (the synthetic local accounts alex@example.test and bob@example.test linked to customers C-1 and C-2, and Bob's order O-2001, plus the Studio workspace W-1 and the Travel workspace W-2 with one note each; a newly created fixture account gets the course-only password written in prisma/fixtures.ts, an existing account keeps its password). The seed and fixture scripts refuse any database other than the local shopfront_dev or shopfront_test. To open the app, run `npm run api` in a second terminal (the public catalog still reads its sample catalog API on http://127.0.0.1:5211) and `npm run mail` in a third (the local mail sink: SMTP on 127.0.0.1:2525 and a mailbox page at http://127.0.0.1:3041; it accepts only example.test recipients), then, in another terminal, `npm run dev -- --port 3000` and open http://localhost:3000 (the npm scripts bind 127.0.0.1; keep using localhost, the origin in BETTER_AUTH_URL: 127.0.0.1 is a different browser origin). `npm run check` checks the TypeScript code; restart Next after `npm run db:generate` or a change to .env. The integration tests use their own server on http://127.0.0.1:3140 against shopfront_test, with a fresh random secret and no GitHub values: stop the development server first (both use the project's .next folder), then run `npm run test:auth`. The launcher refuses any TEST_DATABASE_URL that is not a local shopfront_test, prepares that database itself and stops its own server whether the tests pass or fail; never run two servers in the same project folder at once. Stop each process with Ctrl+C when you finish.

## Try it

Stop the development server and run `npm run test:auth`: after the setup every assertion passes, and the launcher stops its server and returns control to the terminal. A failing check prints the expected and actual status codes: fix the boundary that behaved differently, never the assertion. The changed note and the expired session stay in shopfront_test; your development data is unchanged.
