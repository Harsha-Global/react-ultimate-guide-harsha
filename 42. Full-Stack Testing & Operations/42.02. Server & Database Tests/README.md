# Server & Database Tests

Starter/shopfront-next is the incoming guided application. Completed/shopfront-next is the demonstrated checkpoint. Continue your working copy or use a separate Starter/Completed copy; never combine their build folders.

Support Files contains the supplied helpers and references used in this lecture:

- `shopfront-next/operations/database-tests.txt`
- `shopfront-next/tests/constraints.integration.ts`

## Run

Work in C:\react\shopfront-next: continue your own working copy there, or copy this ZIP's Starter (to follow the video) or Completed shopfront-next folder there. No folder anywhere in the path may contain the & character, so never run npm inside the extracted section folder. Open the folder in VS Code. The ZIP leaves out the private .env file and Prisma's generated client (generated/): you create both below.

PostgreSQL must be running with the course role shopfront and its two databases, shopfront_dev (development) and shopfront_test (automated tests only), as set up in Setting the Environment: in SQL Shell, as the postgres administrator, `CREATE ROLE shopfront LOGIN;`, `\password shopfront` (a private password), `CREATE DATABASE shopfront_dev OWNER shopfront;` and `CREATE DATABASE shopfront_test OWNER shopfront;`. Reuse existing course databases; never drop or reset one.

Copy .env.example to .env (Git ignores it) and enter your own private values: in DATABASE_URL and DIRECT_URL (both shopfront_dev) and TEST_DATABASE_URL (shopfront_test) replace REPLACE_ME with the shopfront role's password, and 5432 with your PostgreSQL port if you chose another one. URL-encode special characters in that password (for example @ as %40, : as %3A, / as %2F, # as %23, % as %25), or they are read as parts of the connection string. Keep COURSE_ALLOW_WRITES=disabled in .env, in an .env.local left from the previous section, and in the terminal before you start Next (PowerShell: `$env:COURSE_ALLOW_WRITES="disabled"`; macOS/Linux: `export COURSE_ALLOW_WRITES=disabled`): a terminal value or .env.local takes priority over .env. Set BETTER_AUTH_URL=http://localhost:3000 and replace the BETTER_AUTH_SECRET placeholder with your own random secret, generated privately with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"` (never share it or commit it). GITHUB_CLIENT_ID and GITHUB_CLIENT_SECRET stay optional (OAuth Sign-In; callback http://localhost:3000/api/auth/callback/github): leave them empty to hide the GitHub button. Keep the local mail values from .env.example (SMTP_HOST=127.0.0.1, SMTP_PORT=2525, SMTP_SECURE=false, empty SMTP_USER and SMTP_PASSWORD, an example.test MAIL_FROM).

Stop any other app using ports 3000, 5211, 2525, 3041, 3140 or 3240 first. In a first terminal run `npm ci` (the first installation needs registry access), then `npm run db:check`: it prints the connected database (shopfront_dev) and user (shopfront), never the password. Then run `npm run db:deploy` (applies the saved migrations to shopfront_dev; a repeated run reports none pending), `npm run db:generate` (writes Prisma's typed client into generated/; rerun it, and restart Next, after every schema change) and `npm run db:seed` (the sample customers, products and order; safe to repeat, and it restores the sample stock), then `npm run db:fixtures` (the synthetic local accounts alex@example.test and bob@example.test linked to customers C-1 and C-2, and Bob's order O-2001, plus the Studio workspace W-1 and the Travel workspace W-2 with one note each; a newly created fixture account gets the course-only password written in prisma/fixtures.ts, an existing account keeps its password). The seed and fixture scripts refuse any database other than the local shopfront_dev or shopfront_test. To open the app, run `npm run api` in a second terminal (the public catalog still reads its sample catalog API on http://127.0.0.1:5211) and `npm run mail` in a third (the local mail sink: SMTP on 127.0.0.1:2525 and a mailbox page at http://127.0.0.1:3041; it accepts only example.test recipients), then, in another terminal, `npm run dev -- --port 3000` and open http://localhost:3000 (the npm scripts bind 127.0.0.1; keep using localhost, the origin in BETTER_AUTH_URL: 127.0.0.1 is a different browser origin). `npm run check` checks the TypeScript code; restart Next after `npm run db:generate` or a change to .env. The integration tests use their own server on http://127.0.0.1:3140 against shopfront_test, with a fresh random secret and no GitHub values: stop the development server first (both use the project's .next folder), then run `npm run test:auth` and, with `npm run mail` running, `npm run test:recovery`. The launcher refuses any TEST_DATABASE_URL that is not a local shopfront_test, prepares that database itself and stops its own server whether the tests pass or fail; never run two servers in the same project folder at once. Stop each process with Ctrl+C when you finish.

Stripe (sandbox only): sign in to your own Stripe account, select a sandbox (test data), open Developers > API keys and copy its secret key privately into STRIPE_SECRET_KEY in .env (it must start with sk_test_ or rk_test_; the app rejects any other key, and you never add a live key). Leave STRIPE_WEBHOOK_SECRET empty until the webhook lecture. Restart Next after changing .env.

Stripe webhooks (sandbox only): install the Stripe CLI (the video uses the official 1.53.1 Windows release zip from github.com/stripe/stripe-cli/releases, extracted to C:\react\tools\stripe-cli and added to the terminal's PATH for that session), run `stripe login` and authorize the same sandbox that your STRIPE_SECRET_KEY belongs to. In a separate terminal run `stripe listen --all-snapshot --forward-to http://localhost:3000/api/stripe/webhook` (this CLI version requires an event selector) and keep it running; put the signing secret it prints (whsec_â€¦) into STRIPE_WEBHOOK_SECRET in .env, privately, and restart Next. The listener's secret is not the same as a hosted webhook endpoint's secret.

Local object storage (SeaweedFS 4.48, local only): download the official Windows archive windows_amd64.zip from github.com/seaweedfs/seaweedfs/releases/tag/4.48 (the video saves it to C:\react\Downloads and checks its SHA-256 FE90C04C0620AD1A1C756F86CD5E1443773F56A446688077A4BB5EC04C3CC874), extract it so that weed.exe is at C:\react\tools\seaweedfs\weed.exe, and copy the SeaweedFS block of .env.example into .env (WEED_BINARY with your actual weed.exe path, S3_ENDPOINT=http://127.0.0.1:8333, S3_REGION, S3_BUCKET and the disposable local S3_ACCESS_KEY / S3_SECRET_KEY; never reuse them for hosting). Run `npm run storage` in its own terminal and keep it running: it binds every SeaweedFS listener to 127.0.0.1 and allows only your BETTER_AUTH_URL origin. On its first start Windows may show a firewall prompt for weed.exe; the course needs only loopback access, so you can cancel it. The data lives in .local-storage (Git ignores it). Stop any other app using ports 8333, 8888, 9333 or 9340 first.

Private uploads (local only): `npm run storage` starts the course SeaweedFS server on 127.0.0.1:8333 (S3 API) with its data in .local-storage; keep it running in its own terminal while you upload or run the upload tests.

Local receipt jobs: keep INNGEST_DEV=1 and leave the cloud signing/event keys empty for local work. Run `npm run jobs` in a separate terminal when checking receipt or outbox processing. The inherited pinned Inngest runner installer permission is already declared in package.json. Its local dashboard is http://127.0.0.1:8288 and it registers the app at /api/inngest. Keep the app and runner running together. Hosted deployment uses INNGEST_DEV=0 and separate cloud credentials, as described in the supplied deployment guide.

## Real server and database tests

Stop the development app, then run `npm run test:input` and `npm run test:database`. The guarded launchers use only local shopfront_test; they create their own test server and fixtures.
