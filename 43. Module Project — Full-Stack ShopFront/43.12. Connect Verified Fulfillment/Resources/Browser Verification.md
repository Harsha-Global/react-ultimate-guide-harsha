# Browser verification scenarios

Run against the exact completed source and configured local origin. Use separate Alex/Bob contexts; fixtures are local. The final author run used the production build and installed Chrome. Assertions are in Author Evidence; the following sequence is also a recorder checklist.

1. Open /catalog and the lamp's direct address. Confirm four seeded products, local fonts/images, categories and shortlist. In the "Connect the Public Catalog" lecture or later, temporarily stop only the teaching API and reload the public catalog; restart it for earlier labs.
2. Anonymous /orders/O-1001 must show Please sign in. Alex sees O-1001 and $145; Bob sees only his own order, and Alex's direct URL is unavailable. Repeat after logout, back and reload.
3. Alex's W-1 order portion is lamp $89; Bob's W-2 portion is two mugs $56. Check a viewer and direct rejected stock request. Submit an old expectedStock after another write; preserve the newer database value and retained draft. Refresh deliberately after copying any unsaved draft.
4. Apply each status filter. Check URL, reload, Clear, back/forward, unknown value and repeated parameters. An unauthorized workspace remains unavailable. Inventory stays visible in an empty filtered queue. Tab from the select to Apply filter, then Clear; keep visible focus.
5. From the "Create Retry-Safe Purchases" lecture onward, after stopping the normal Next/APIservers, run npm run test:browser -- tests/browser/purchase-recovery.spec.ts from the learner project. The supplied3-test scenario uses the existing isolated launcher and shopfront_test; add --debug for Inspector/visible step-by-step capture. At the product page, let POST /api/workshop/orders commit, then deliberately drop only its response in this controlled local browser test. Keep the same tab, reload and click Retry this order attempt. Its complete payload must match the original, and the returned order ID must be identical. A request abort alone does not prove rollback. Do not manually create a second key as a recovery step.
6. Use the controlled paid fixture for a ready merchant fulfillment. Mark dispatched; confirm it leaves the ready view and appears under dispatched. Repeating the POST must preserve one row. Viewer, wrong workspace and wrong origin requests must fail.
7. Follow Recording Preflight for actual local outbox/job interruption and receipt page refresh, plus storage interruption, recovered upload and Bob's private-image denial.
8. Check360/390px widths, a desktop viewport, long generated order IDs, complete button labels, form errors and keyboard access. Inspect the actual rendered screen; a scrollWidth assertion alone does not establish visual quality.

For the merchant order notes challenge, save trimmed text, reject whitespace, hold a request to observe disabled pending controls, keep two editor pages at the same revision, and reject the stale save. Commit a note then drop its response: preserve the draft, copy it, refresh to inspect saved state, and retain the filter URL. A viewer reads the note but has no edit form and cannot PATCH it. Customer responses contain no merchant note.

The tests use their own isolated local server/database. The delivered Playwright configuration uses its installed Chromium browser. If this machine has not installed it, run npx playwright install chromium. A PLAYWRIGHT_CHANNEL environment variable does not override this configuration. Dated author evidence identifies any separate author harness that used installed Chrome.
